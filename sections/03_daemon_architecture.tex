\chapter{Daemon Architecture} \label{chapt:daemon}

\section{Overview}

When user installs Wayclip, either the CLI or the APP, a \lstinline|wayclip-daemon| binary is also installed.
The daemon itself is a single Rust process built around one orchestrator, DaemonCore. DaemonCore controls the whole daemon using its various modules.
The generally hierarchy as shown in Figure~\ref{fig:ownership}, illustrates those modules which consist of DaemonIpc (responsible for communications), DaemonServices (non-essential extras such as hotkeys and tray) and DaemonEngine (responsible for ring and frame capture).

\section{Video \& Audio Pipeline}

As shown previously, the video and audio pipeline are made inside DaemonEngineGStreamer, using its internal pipelines. We created wrappers around those gstreamer elements to make it easier to build more pipelines in the future, by assigning values and properties to the name in a separate module.
The video branch is adapted to support NVIDIA, AMD and Intel GPU's. If no GPU is present, we are able to fallback to software encoders too. This is achieved by first capturing the connection data provided by the portal itself, which is then fed into \lstinline|pipewiresrc| elements.
These elements use pipewire node ID's to capture those specific input, and after routing them through filters and processing stages, we can insert them into an AppSink. These app sinks also come from the GStreamer library, and are responsible for containing the data and passing it into the ring buffer.

Audio follows a same pattern, but instead of one source, we have two. We acquire the PipeWire node ID for the audio devices, then captured by a standalone \lstinline|pipewiresrc| (for microphone and background audio) they are mixed together into a single stream and later encoded.

Figure~\ref{fig:pipeline} shows the chain for NVIDIA specifically, where the Ring Buffer will keep the latest N seconds always available, and on command, will take a snapshot of that data and write it to a file. More specifically, when user saves a clip we dont clear the data inside, we just take a so-called "snapshot" of the data.
Then we build a second short-lived pipeline on a separate thread and pipe that data into an AppSource, allowing us to not re-encode the frames and directly send them to the muxer. These frames are then written to a file, and all of this is done in the background to keep the daemon running, where once the save is complete, we signal using the \lstinline|mpsc| channel.

It is also important to note that the ring buffer does not store the raw frames -- that would eat up your RAM way too aggressively -- instead, it stored the already encoded ones. The buffer is limited by a simple principle, where upon a frame being pushed inside, we check the total time limit, and if it exceeds the maximum setting -- we prune the oldest frames.

There have been many issues with DMA buffers, and the way they are handled. In short, DMA buffers are raw frames coming from a full-screen source, like a game, which can be copied directly. This is useful as it is usually more efficient and does not require capturing the system itself, only frames coming directly from the game.
In some major titles that we have tested, DMA buffers are a necessity, without them the screen is just blank. Unfortunately, DMA buffers are quite painful to handle in some environments.
Upon setting the caps filter to only accept DMA Buffers, if the input switches for any reason whatsoever -- be it alt-tabbing, or a random switchup, or any other cause -- the pipeline would stall and eventually come to a fail. For this specific reason, we have implemented many health detection systems, as well as recovery procedures.

Problems are detected in three main ways: Errors/EOS signals coming from the pipeline, a stall check (which triggers if no video frames arrive for >=10 seconds), and a guard (which notices when every single frame is being dropped).
Then, depending on what was detected, recovery also has four stages. A quick restart (switching the caps), restarting the pipeline in place, downgrading to system memory, and a full pipeline rebuild.
However, recoveries are also not retried instantly -- each attempt waits a bit longer than the last (following a ladder). After 30 seconds of healthy video, the counter resets back to a normal state.

\section{Event Loop}

Once the setup was complete, and the daemon is active, the daemon now enters the event loop stage as shown in Figure~\ref{fig:event_loop}.
The event loop is a \lstinline|tokio::select!| statement which sleeps until any input is ready. The inputs include a termination signal, command from the IPC, GStreamer events, Save Results and the tick timer for DaemonServices.
